# meteocool iOS — agent notes

Native Swift/UIKit iOS app. The map view itself is a web view rendering
[meteocool/core](https://github.com/meteocool/core); everything else
(settings, onboarding, location, push notifications) is native.

## The Xcode project is generated — never edit it

`meteocool.xcodeproj` is **generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen)
from [`project.yml`](project.yml)** and is gitignored. Editing the project in
Xcode's UI and committing it does nothing; the next `xcodegen generate` throws
it away.

To change targets, sources, dependencies or build settings, edit `project.yml`
(or the xcconfigs in `Config/`) and regenerate:

```
xcodegen generate
```

Build settings live in three places, in precedence order:

| Where | What belongs there |
| --- | --- |
| `Config/Base.xcconfig` | shared identity + versioning (`BUNDLE_PREFIX`, `DEVELOPMENT_TEAM`, `MARKETING_VERSION`, `CURRENT_PROJECT_VERSION`) |
| `Config/{Debug,Release}.xcconfig` | per-configuration optimization/debug flags |
| `project.yml` | per-target settings (bundle ids, Info.plist, entitlements) |

`Local.xcconfig` (gitignored, optional — see `Local.xcconfig.example`)
overrides signing identity per machine.

## Build commands

Everything runs headless; no Xcode UI required.

```bash
# Regenerate the project after editing project.yml
xcodegen generate

# Fast unsigned compile check (simulator) — use this for iteration
./scripts/build.sh

# Build, boot a simulator, install and launch
./scripts/run.sh

# UI tests on a simulator
./scripts/test.sh

# Signed device archive + install over USB via devicectl
./scripts/device.sh

# Archive + export a signed App Store .ipa into build/Export
./scripts/release.sh

# Bump Swift package dependencies and rewrite ./Package.resolved
./scripts/update-packages.sh
```

Dependency versions are pinned in `./Package.resolved` at the repo root, not in
the generated workspace — the scripts copy it into
`meteocool.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/` after each
`xcodegen generate`. If you run `xcodegen generate` by hand and want the pins
honoured, copy it yourself or just use the scripts.

The raw commands behind those scripts:

```bash
# Unsigned simulator build (no certificates needed)
xcodebuild -project meteocool.xcodeproj -scheme meteocool \
    -destination 'generic/platform=iOS Simulator' \
    CODE_SIGNING_ALLOWED=NO build

# Signed device archive
xcodebuild -project meteocool.xcodeproj -scheme meteocool \
    -destination 'generic/platform=iOS' -allowProvisioningUpdates \
    -derivedDataPath build/ios \
    archive -archivePath build/meteocool.xcarchive

# List attached devices / install
xcrun devicectl list devices
xcrun devicectl device install app --device <UDID> path/to/meteocool.app
```

## Targets

| Target | Type | Notes |

| `meteocool` | app | main app; embeds the notification service extension |
| `NotificationService` | app extension | mutates incoming pushes (`UNNotificationServiceExtension`) |

The legacy *Today* widget (`Widget/`, `NCWidgetProviding`) was removed during the
XcodeGen conversion: it had not been embedded in the app for years and iOS 18+
no longer displays Today widgets at all. A home-screen widget would be a new
WidgetKit extension; `git show c503a8c:Widget/TodayViewController.swift` has the
old code if it is ever useful as a reference.

## CarPlay

The car screen is a second scene, declared in `Info.plist` under
`CPTemplateApplicationSceneSessionRoleApplication` and owned by
[`meteocool/CarPlay/CarPlaySceneDelegate.swift`](meteocool/CarPlay/CarPlaySceneDelegate.swift).
CarPlay splits a map app in two: templates, which the system draws and which are
the only thing the driver can touch, and the map itself — an ordinary
`UIViewController` in the `CPWindow` underneath. There is nothing worth putting
in a template yet, so the root template is an empty `CPMapTemplate` and the whole
screen is `CarPlayMapViewController`: the same web map, loaded from
`MeteocoolEnvironment.carPlayURL` (`ios.html?…&toolbar=no`) so it comes up
without the toolbar or the forecast strip.

Two consequences worth knowing before touching any of it:

- **The entitlement is Apple's to grant.** Drawing into a `CPWindow` at all
  requires `com.apple.developer.carplay-maps`, requested per app at
  <https://developer.apple.com/contact/carplay/>. Apple has not granted it yet,
  so the key is not in `meteocool/meteocool.entitlements`: with it, anything
  that signs (`scripts/device.sh`, `scripts/release.sh`, `fastlane beta`) fails
  with a provisioning-profile error. Signed builds do not appear on the car
  screen until it is granted and the key is added back. Unsigned simulator
  builds do not care.
- **CarPlay forces `UIApplicationSupportsMultipleScenes`.** On iPadOS that also
  offers the user a second copy of the phone UI, which the map cannot survive —
  `ViewController` publishes itself into a global `viewController` that settings
  and gestures then talk to. `SceneDelegate.scene(_:willConnectTo:options:)`
  destroys any additional window scene for that reason.

Location is the one piece of shared state. `LocationUpdater` normally drops to
significant-change updates when the app leaves the foreground, which moves the
map about once a kilometre; with the phone locked in a pocket that is exactly
when the car screen needs real updates, so `carPlayConnected` suspends the
downgrade and observers are notified regardless of application state.

## Environments

**Mode** (under About in Settings) picks one of three: **Production** (`app`,
`app.meteocool.com`, the default), **Experimental Features** (staging) or
**Demo**. It is stored as `environment` and takes effect without a restart:
`MeteocoolEnvironment.select(_:)` posts `didChange`, the phone and CarPlay maps
reload, and `NotificationManager` moves a push registration (removed from the
old API, then made on the new one). The two switches Mode replaced are migrated
once: Demo Mode carries over, Experimental Features goes back to Production. The
URLs live in [`meteocool/lib/Environment.swift`](meteocool/lib/Environment.swift)
— never hardcode a host at a call site:

| | App (default) | Staging | Demo |
| --- | --- | --- | --- |
| Web map (`WKWebView`) | `app.meteocool.com/ios.html` | `next.meteocool.com/ios.html` | `demo.meteocool.com/ios.html` |
| Native API (`NetworkHelper`) | `app.meteocool.com` | `api-next.meteocool.com` | `api-demo.meteocool.com` |

`app.meteocool.com` belongs to no environment of its own. It is a custom domain
of one of core's Workers (currently staging's, see core/wrangler.jsonc), and that
Worker forwards the app's API calls to its own backend (core's `worker/api.ts`).
The production cutover is therefore a change in core, not an app release: move
the domain to the production Worker and move the push registrations from
staging's database to production's in the same step. Otherwise staging goes on
notifying the phones too, because the app sees the same URL and never
unregisters from staging.

Demo is the staging code in its own namespace, replaying a recorded storm as if
it were happening now.

Staging is the rewritten backend from [meteocool/ng](https://github.com/meteocool/ng)
plus the `--mode staging` build of [meteocool/core](https://github.com/meteocool/core).

The web map and the native API must move together: each frontend build is built
against one backend's contract, and a push registration posted to the wrong
cluster never produces a notification.

### Talking to the v4 backend

`post_location`, `clear_notification` and `unregister` are unversioned routes
served by ng's legacy compatibility router (`services/api/src/routers/legacy.py`),
which accepts the payloads the shipped apps already send and fans them out to
`/v3/mobile` and `/v3/telemetry`. Its validation is stricter than the old Flask
service, and it answers `200 {"success": false}` rather than a 4xx, so a
malformed field looks like success at the transport layer while silently
dropping the registration *and* the barometric reading. Known constraints:

- `lang` must be `de` or `en` (`Language` enum) — `LocationUpdater` clamps it.
- `ahead` must be `> 0` and `<= 60` minutes.
- `intensity` is dbZ, `0...130`.
- `withDBZ` is the key the v4 backend reads; the old backend reads `details`.
  Both are sent, and each deployment ignores the other's key.
- `token` must be 32–192 characters.

## Location

The app never lets the web view geolocate itself. It owns a `CLLocationManager`
(`meteocool/lib/LocationUpdater.swift`) and pushes every fix into the page as
`window.lm.updateLocation(lat, lon, accuracy, zoom, focus)`, because a
`navigator.geolocation` call inside a `WKWebView` raises WebKit's own per-origin
alert on top of the permission the app already holds — a second prompt for
something the user granted once.

Gating the call in the frontend only covers the call sites the frontend knows
about, so [`meteocool/lib/GeolocationBridge.swift`](meteocool/lib/GeolocationBridge.swift)
closes it at the source: a document-start `WKUserScript` replaces
`navigator.geolocation` with a shim that posts to the `geolocationHandler`
message handler, and `ViewController.serveGeolocationRequest()` answers it out
of CoreLocation. `getCurrentPosition`, `watchPosition` and `clearWatch` all work
inside the web view; WebKit's geolocation machinery is never reached, so no
prompt can appear. The same fix that drives `updateLocation` is handed to the
shim from `notify(location:)`, which is what keeps watchers updating.

## UI chrome

The map screen is a `WKWebView` with native controls floating on top of it
(`Main.storyboard` + `ViewController`). On iOS 26 those controls are Liquid
Glass, built in [`meteocool/lib/LiquidGlass.swift`](meteocool/lib/LiquidGlass.swift):

- the `TribbleButton` slab behind the layer/settings/location buttons is
  dropped and the buttons are reparented into a `UIGlassContainerEffect` —
  glass cannot sample other glass, so neighbouring elements have to share a
  container or they drift apart visually;
- the status bar backdrop becomes glass too, and the settings tables scroll *under* their navigation bars,
  because a glass bar with nothing passing beneath it renders as a flat slab.

Everything is behind `if #available(iOS 26.0, *)`; the deployment target is
iOS 18, which keeps the shipped blur-and-PNG look. Glass is for the
navigation layer only — the radar map itself is content and stays untreated.

The iOS 27 SDK refuses to launch an app that has not adopted the UIScene life
cycle, so `SceneDelegate` owns the foreground/active hooks that used to sit on
`AppDelegate` (those `application…` callbacks stop firing once
`UIApplicationSceneManifest` is present in `Info.plist`).

## AR storm view

`meteocool/AR/` draws the same storm volumes as core's 3D map over the camera
image (`ARStormViewController`). What is easy to get wrong:

- **The volumes are voxels, not meshes**: ng's `.mcvx` (dBZ and confidence
  bytes), raymarched in `StormShaders.swift`, a port of core's shader. Keep
  its constants in step with core's `src/layers/cellVolumeLayer.ts`.
- **A storm is many boxes.** Since 2026-10-05 ng boxes storms by Web Mercator
  tile (zoom 10, about 26 km; zoom 11 at cores; a coarse zoom-9 tile per
  run, listed only with `?coarse=true`), each with a one-voxel `apron` of its
  neighbours that is sampled but never drawn. Tiles of one storm share a
  `system`: `StormGroup` is one storm, with one tag, selection, peel floor and
  cut plane, and the two-layer limit counts storms, not tiles. Volumes are
  held by bytes (`StormFeed.residentBytes`), and storms past 90 km draw their
  coarse tiles. Boxes from before tiles (`G` codes, no `tile`) still work.
- **Shaders compile at run time** from `StormShaders.source`; there is no
  `.metal` file, so the build needs no Metal toolchain. The Swift mirrors of
  the uniform structs sit beside the source, and `scripts/check-ar.sh`
  compares them with Metal's layout.
- **At most two layers of cloud per pixel.** Storms are drawn near to far,
  each reading the pixel it draws to (`STORM_FETCH`); behind two storms that
  drew real cloud, or behind opaque cloud, nothing is marched. The iOS
  simulator's compiler refuses that, so there the renderer falls back to far
  to near through the blender. `scripts/check-ar.sh` checks both on the Mac's
  GPU with three storms in a row.
- **Placement goes through ECEF**, never a flat map: curvature moves a storm
  at 60 km by about 280 m. The world is ARKit's (x east, y up, z south);
  `HeadingAlignment.error` corrects ARKit's compass north (compass blend, drag
  nudge, sun tap, geo tracking).
- **Data hosts** are `MeteocoolEnvironment.dataBaseURL` and `assetBaseURL`.
  On app both are app.meteocool.com, which core's Worker forwards; see the
  environment section above.
- **Palettes** come from core: rerun `scripts/colormaps.py <core>` to
  regenerate `AR/Colormaps.swift`.
- Landscape is allowed only while the AR view is presented
  (`AppDelegate.application(_:supportedInterfaceOrientationsFor:)`).
- **Callbacks ARKit, Metal or Core Location deliver on their own queues
  must be `@Sendable` closures.** Swift 6 otherwise infers main-actor
  isolation for a closure written in main-actor code, checks it when the
  closure runs, and traps on any other queue
  (`ARGeoTrackingConfiguration.checkAvailability` crashed the first phone
  build this way). The same goes for notifications iOS posts off the main
  thread: observe `ProcessInfo.thermalStateDidChangeNotification` with
  `queue: .main`, never with a selector. The simulator has no ARKit and never
  changes thermal state, so only a device finds these.
- Without ARKit (the simulator) the same view runs as a drag-to-look preview.
  The AR button shows only while the `HiddenFeatures` are on (five taps on
  the logo) and where AR works, or as the preview in debug simulator builds.
  The page's "View in AR" follows the same switch; flipping it reloads the map,
  because the page reads `nativeCapabilities.ar` only at load.

## App icon

`meteocool/AppIcon.icon` is an Icon Composer document **generated by
[`scripts/app-icon.py`](scripts/app-icon.py)**; change the script and rerun it
rather than editing the layers. It is the only icon source: Xcode renders the
Liquid Glass icon from it on iOS 26+ and flattens it for iOS 18–25. It is the
original cloud logo: the document's fill is the background (white, near-black
when dark), with two glass groups on it — the clouds with their outline, and
the raindrops. Preview renditions with `ictool` (usage in the script's
docstring).

## Shared state

App and extensions share `UserDefaults(suiteName: "group.org.frcy.app.meteocool")`.
That identifier is hardcoded in Swift *and* in the `.entitlements` files — if you
change `BUNDLE_PREFIX`, change it in both places too.

## Releasing

`fastlane beta` (see `fastlane/Fastfile`) bumps the build number and uploads to
TestFlight. `./scripts/release.sh` produces the same signed `.ipa` locally
without fastlane.

### Xcode Cloud

Xcode Cloud never sees a committed project, so
[`ci_scripts/ci_post_clone.sh`](ci_scripts/ci_post_clone.sh) installs XcodeGen,
runs `xcodegen generate` and copies `./Package.resolved` into the generated
workspace. Xcode Cloud runs it after cloning and before opening the project.
It must stay executable (`chmod +x`), or Xcode Cloud skips it without saying so,
and `ci_scripts/` must stay next to `meteocool.xcodeproj`.

The workflow itself (start condition, Archive action, TestFlight post-action,
Xcode version) is configured in Xcode or App Store Connect, not in the repo.
The workflow stores only the project path and the scheme name, and XcodeGen
generates shared schemes, so regenerating the project does not affect it.

- **Build numbers.** Xcode Cloud assigns its own build number and ignores
  `CURRENT_PROJECT_VERSION`. Set the next number in App Store Connect
  (Xcode Cloud → Settings → Build Number) above the latest TestFlight build.
  `fastlane beta` also bumps from the latest TestFlight build, so use only one
  of the two for TestFlight uploads.
- **Signing** is cloud-managed from `DEVELOPMENT_TEAM`. `Local.xcconfig` does
  not exist there, which is fine because it is an optional include.
- **CarPlay.** Adding `com.apple.developer.carplay-maps` before Apple grants it
  breaks the cloud archive the same way it breaks `scripts/release.sh`.

## Audit changes (21 September 2026)

Use Xcode 27. Scripts default `DEVELOPER_DIR` to `/Applications/Xcode.app/Contents/Developer`
without changing global selection. Deployment target is iOS 18; UIKit glass is
available on iOS 26 and 27.

The web frontend owns forecast playback. The obsolete native forecast drawer
and its custom gesture recognizer were removed because its JavaScript entry
points no longer exist. Native settings use UISlider; StepSlider was removed.

`NotificationManager` owns opt-in, foreground authorization refresh, token
registration, removal and visible sync-failure state. Stored APNs tokens are
used only for removal; new registrations need the current launch's APNs token.
A registration records the API it was posted to (`registrationOrigin`) when it
is sent, not when it finishes, so one in flight during a Mode switch is still
removed from the API it reached.

Onboarding is one sequence and denial/skip are valid completion paths. Location
starts with When In Use; background access is requested separately for alerts.
Pressure is optional and must not delay registration indefinitely or trigger
an unrelated permission prompt.

Run `bash scripts/check.sh` for network, geolocation, notification fallback and AR storm view checks.
The UI tests use `--ui-test-reset`, supported only in Debug simulator builds,
to reset app preferences between cases. They do not reset OS permissions.

Onboarding is SwiftUI (`meteocool/onboarding/OnboardingView.swift`) hosted in a UIHostingController sheet: a welcome feature list, then Location, then Rain Alerts. Location comes first so the background upgrade requested after alerts builds on When In Use. Pages scroll so large text does not truncate, and at accessibility sizes the buttons scroll with the page rather than being pinned. Buttons are glass on iOS 26 and later. Both former Swift packages (OnboardKit and StepSlider) are removed; the retained package lock has no pins. Settings rows wrap and self-size.

The production web host follows core/wrangler.jsonc. Its currently deployed UI differs from staging and fails the rewritten playback accessibility test. Run that test against production before releasing. Switching environments removes the last recorded registration from its original API before registering on the new API.

## Map loading

Nothing about the map page waits for the user. [`MapRecovery`](meteocool/lib/MapRecovery.swift)
reloads it when the navigation fails, when it does not post `requestSettings`
in time, when the web content process dies (memory, GPU), when a canvas in
`#map` loses its WebGL context for good (a document-start script reports
`mapGraphicsLost`), and when it no longer answers on returning to the
foreground. Retries back off from 1 to 15 seconds and happen at once when the
network returns or the app comes back. A status ("Trying again…") appears from
the second failure; it is not a button.

The logo goes home: a tap closes the page's panels (a synthetic Escape) and
switches the web map back to the radar (`window.lm.setTarget("radar", "map")`).
Five taps in a row toggle [`HiddenFeatures`](meteocool/lib/HiddenFeatures.swift),
off at every launch; the AR storm view is offered only while they are on.
